# خطة الوصول إلى جاهزية تشغيلية 97% — دكتره ERP

**الهدف:** رفع الجاهزية من تقييمها الحالي—**68% بناء برمجي، 61% ترابط، و38% جاهزية محاسبية إنتاجية**—إلى **97% جاهزية تشغيلية قابلة للقياس**. لا تعني نسبة 97% خلو البرنامج من جميع المخاطر، بل تعني اجتياز بوابات قبول محددة، وتوثيق الاستثناءات المتبقية، وإجراء تشغيل مراقب قبل الاعتماد الكامل.

> **قاعدة الحوكمة:** لا تنتقل أي مرحلة إلى التي تليها إلا بعد نجاح اختبارات القبول الخاصة بها، وحفظ نقطة تفتيش مستقرة، واعتماد نتيجة المرحلة. لا يُمنح الربط الحكومي أو الإطلاق الإنتاجي صفة «مكتمل» بمجرد وجود واجهة أو طابور داخلي.

## مؤشرات القياس النهائية

| المحور | معيار 97% | دليل القبول |
|---|---|---|
| صحة البيانات | لا فروقات غير مبررة بين schema.ts وقاعدة البيانات | `pnpm db:verify` وتقرير تدقيق محفوظ |
| المحاسبة | كل دورة تشغيلية تنشئ قيداً متزناً وقابلاً للمطابقة | سيناريوهات UAT وميزان مراجعة ومطابقة حسابات |
| التشغيل | لا تكرار للحركات أو خصم غير مصرح أو رصيد سالب | اختبارات تكامل وحالات استثناء موثقة |
| الصلاحيات | كل إجراء حساس محكوم بصلاحية ونطاق وتدقيق | تقرير route–permission واختبارات سماح/رفض |
| الاستعادة | استعادة نسخة مشفرة إلى بيئة معزولة بنجاح | سجل RPO/RTO ونتيجة الاستعادة |
| زاتكا | فواتير اختبار موثقة في Sandbox قبل الإنتاج | CSID/CSR، نتائج الامتثال والاستجابات الرسمية |
| الأداء والأمن | أحمال ومسارات حساسة ضمن الحدود المتفق عليها | تقرير اختبار تحميل وأمن ومعالجة النتائج |

## المرحلة 1 — تثبيت baseline تقني وتشغيلي

**الهدف:** منع الانجراف بين الشيفرة والمخطط وقاعدة البيانات، وتحديد سياسة ترحيل واحدة قابلة للتكرار.

| العمل | الناتج | قبول المرحلة |
|---|---|---|
| اعتماد `schema-audit` كفحص إلزامي | تقرير جداول/أعمدة/قيود | صفر فروقات غير مبررة |
| توثيق الترحيلات اليدوية المطبقة | سجل migration ledger | كل تعديل SQL له ملف مرجعي وحالة تطبيق |
| منع تشغيل توليد Drizzle التفاعلي في الإنتاج | سياسة ترحيل آمنة | استخدام تحقق ومراجعة قبل التطبيق |
| تثبيت أمر تحقق موحد | `pnpm db:verify` | ينجح مع TypeScript والاختبارات والتدقيق |

**بوابة الخروج:** لا فروقات مخطط، ولا ترحيل غير موثق، وحفظ نقطة تفتيش.

## المرحلة 2 — الأمن وRBAC الذري

**الهدف:** أن يكون كل فعل حساس قابلاً للتفويض والمراجعة حسب الدور والفرع والمخزن ومركز التكلفة.

| العمل | معيار القبول |
|---|---|
| إكمال نطاق مركز التكلفة في الأدوار والتجاوزات | اختبار سماح ورفض على عملية حساسة |
| تغطية الأزرار والإجراءات في الواجهة | لا يظهر أو ينفذ فعل غير مسموح |
| مدقق route–permission | لا mutation حساسة بلا صلاحية ذرية أو استثناء موثق |
| مراجعة `protectedProcedure` و`adminProcedure` | تحويل العمليات الحساسة أو توثيق الاستثناءات |
| تعزيز جلسات الإدارة | انتهاء جلسات، إلغاء جلسة، تغيير كلمة المرور، سجل تدقيق |

**بوابة الخروج:** مصفوفة صلاحيات معتمدة واختبارات أدوار واقعية متعددة النطاق.

## المرحلة 3 — المحاسبة العامة والقيود التلقائية

**الهدف:** أن تتحول الحركات التشغيلية إلى قيود متزنة ومطابقة وقابلة للإقفال.

| الدورة | القيد المطلوب | اختبار القبول |
|---|---|---|
| استلام شراء | مخزون/ضريبة مدخلات مقابل مورد أو استحقاق | ربط الفاتورة بالاستلام والقيد |
| بيع POS | نقد/مدين مقابل مبيعات وضريبة مخرجات | مطابقة الطلب والفاتورة والقيد |
| إنتاج | منتج تام مقابل مواد/انحراف | مطابقة الاستهلاك والتكلفة والقيد |
| هدر/تالف | مصروف هدر مقابل مخزون | إذن متعدد البنود وقيد واحد متزن |
| تحويل/جرد | دون أثر ربحي إلا عند تسوية أو فرق | فروقات الجرد والقيد المعتمد |
| استرداد | عكس بيع/ضريبة/مخزون بسند مرجعي | عدم إلغاء بيع مدفوع مباشرة |

**بوابة الخروج:** شهر UAT واحد مكتمل مع ميزان مراجعة وقوائم ومطابقة حسابات بلا فروقات غير مبررة.

## المرحلة 4 — المطاعم وPOS والمخزون والمشتريات والإنتاج

**الهدف:** استكمال الاستثناءات الواقعية لدورة المطعم متعددة الفروع.

تشمل المرحلة: استرداد وإلغاء مدفوع بسند معتمد، إقفال كاشير يومي، مردودات شراء، استثناءات الإنتاج، التوالف متعددة البنود، bundle/وجبة مع مشروب بخيارات تكلفة، التصنيفات الفرعية للمخزن، وتقارير رصيد وتكلفة افتتاحية/واردة/صادرة/ختامية.

**بوابة الخروج:** سيناريوهات قبول لفرعين ومخزنين وكاشيرين وإنتاج وتحويل وجرد دون ازدواج أو رصيد سالب.

## المرحلة 5 — ضريبة القيمة المضافة وزاتكا

**الهدف:** إكمال VAT محاسبياً، ثم ربط فاتورة في Sandbox رسمياً.

| العمل | الاعتمادية |
|---|---|
| مطابقة ضريبة المدخلات والمخرجات مع دفتر الأستاذ | داخلي |
| QR وXML والتوقيع حسب مواصفات فاتورة | يحتاج CSR/شهادة |
| تهيئة CSID وبيئة Sandbox | يحتاج بيانات المنشأة الرسمية |
| اختبار Reporting وClearance | يحتاج موافقة وبيانات Sandbox |
| اختبار الاستثناءات وإعادة الإرسال وسجل الاستجابات | يحتاج اتصال فعلي |

**شرط خارجي:** لا يمكن إغلاق هذه المرحلة بلا بيانات اعتماد ZATCA الرسمية وموافقة على إرسال فواتير اختبار.

## المرحلة 6 — النسخ والاستعادة واستمرارية الأعمال

**الهدف:** إثبات أن البيانات يمكن استعادتها، لا مجرد إنشـاء نسخة منها.

يشمل ذلك الاستعادة إلى بيئة معزولة، التحقق من سلامة المخطط والبيانات بعد الاستعادة، قياس زمن الاستعادة **RTO** وحد فقد البيانات المقبول **RPO**، وتوثيق إجراء موافقة لاستعادة بيئة الإنتاج.

**بوابة الخروج:** استعادة اختبارية ناجحة وموثقة لنسخة مشفرة.

## المرحلة 7 — UAT ببيانات حقيقية

**الهدف:** نقل الدليل من اختبارات شيفرة إلى اختبار تشغيل حقيقي.

يلزم توفير قائمة الفروع والمخازن والأصناف والأرصدة الافتتاحية والوصفات والضرائب والموردين والعملاء والحسابات الافتتاحية. لا تُستخدم بيانات مختلقة لإثبات الجاهزية المالية. تنفذ السيناريوهات على بيانات UAT أو نسخة معزولة من بيانات التشغيل بعد اعتمادك.

**بوابة الخروج:** توقيع قبول لكل سيناريو، معالجة العيوب الحرجة، وعدم وجود فروقات محاسبية غير مبررة.

## المرحلة 8 — الأداء والأمن واعتماد الإطلاق

يشمل اختبار تحميل POS، اختبار تزامن التحصيل والتحويل، فحص الصلاحيات، اختبار النسخ والاستعادة، مراجعة التنبيهات والسجلات، وخطة إطلاق مراقب لفروع محددة قبل التوسع.

## التسلسل الفعلي والاعتماديات

```text
Baseline → RBAC → قيود تلقائية → تشغيل المطاعم والمخزون
        ↘                   ↘
         نسخ واستعادة        VAT → ZATCA Sandbox
                  ↘          ↙
                    UAT متعدد الفروع
                          ↓
              أداء + أمن + إطلاق مراقب
```

## نقطة البداية المعتمدة

سنبدأ بالمرحلة 1 عبر تثبيت baseline وتشغيل الأمر الموحد للتحقق. بعد ذلك ننتقل إلى المرحلة 2. تعتمد المراحل 5 و7 على مدخلات خارجية منك: اعتمادات زاتكا وبيانات UAT حقيقية، على الترتيب.
