# التقييم المهني لنظام دكتره ERP

**الصفة التقييمية:** مراجعة مستقلة من منظور مدير مالي ومقيّم نظم مالية ومطاعم.

**تاريخ التقييم:** 13 أغسطس 2026.

> **الحكم المختصر:** دكتره يملك أساساً فنياً واعداً وواجهة ERP واسعة، لكنه لا يزال في مرحلة **نموذج تشغيلي متقدم / Pilot** وليس جاهزاً بعد ليكون نظاماً محاسبياً إنتاجياً معتمداً لإقفال مالي أو إقرار ضريبي أو ربط حكومي فعلي. السبب ليس التصميم المرئي؛ بل عدم اكتمال ضوابط دورة المستند–القيد–المخزون–الضريبة، وعدم وجود بيانات تشغيل فعلية تثبت النتائج.

## 1. حدود التقييم والأدلة

تمت مراجعة منطق المعاملات والضوابط في طبقة البيانات وواجهات الصلاحيات والمخطط، وتشغيل اختبارات المشروع، وتدقيق تطابق المخطط وقاعدة البيانات. نجح المشروع في **41 اختباراً**، ولم يرصد مدقق المخطط فروقات بين `schema.ts` وقاعدة البيانات. كما فُحصت اختبارات رقابية للقيود المنشورة، ولم يظهر رصيد مدين أو دائن غير متزن، أو قيود منشورة بلا بنود، أو تكرار لأرقام القيود، أو حركات داخل فترة مغلقة.

لكن قاعدة البيانات التشغيلية كانت خالية من أوامر بيع، قيود يومية، حركات مخزون، فواتير شراء أو مبيعات، أو جلسات نقاط بيع. لذلك تثبت النتائج **سلامة البنية والاختبارات الحالية فقط**، ولا تثبت دقة التشغيل الواقعي أو الإقفال الشهري أو التكاليف الفعلية.

| محور الإثبات | النتيجة | التفسير المالي |
|---|---:|---|
| اختبارات المشروع | 41 ناجحة | تغطية بنيوية ووظيفية أولية، وليست اختبار دورة مالية كاملة. |
| تطابق المخطط وقاعدة البيانات | بلا فروقات | أساس جيد لمنع اختلاف الكود عن البيانات. |
| اختبارات القيود الفعلية | صفر مخالفات | النتيجة محدودة لأن سجل القيود خالٍ. |
| بيانات تشغيلية للاختبار | صفر سجلات في الدورات الأساسية | لا يمكن اعتماد تقارير الربحية أو الضريبة أو الجرد قبل سيناريوهات فعلية. |

## 2. نقاط قوة حقيقية

النظام يتضمن مخططاً جيداً نسبياً للمستخدمين والفروع والمخازن والحسابات والقيود والمبيعات والمشتريات، مع فصل أولي بين الفاتورة الضريبية وسجل الإرسال إلى زاتكا. كما توجد مصادقة محلية بكلمات مرور مجزأة، وجلسات `HttpOnly`، واختبارات لصلاحيات الإدارة. ويعد مدقق تطابق المخطط وقاعدة البيانات نقطة قوة هندسية لا توجد في كثير من الأنظمة الناشئة.

كذلك، فإن قرار فصل طابور زاتكا عن السجل المالي قرار صحيح من حيث المبدأ: ففشل التكامل الخارجي لا ينبغي أن يغير مبلغ الفاتورة أو القيد أو المخزون. هذه نقطة تصميم جيدة، لكنها لا تكفي وحدها للامتثال.

| المجال | التقييم الحالي | الحكم المهني |
|---|---|---|
| دليل الحسابات والهيكل المالي | أساس جيد | يحتاج دفتر أستاذ وإقفال وتسويات قبل الاعتماد. |
| القيود اليومية | غير كافٍ للإنتاج | يحتاج محرك ترحيل ذري وضوابط منع التعديل بعد الترحيل. |
| POS للمطاعم | واجهة أولية واعدة | غير جاهز للنقد والإيراد الحقيقي قبل التسوية والإلغاء والتحصيل والضرائب الصحيحة. |
| المخزون والإنتاج | تصميم مستندات موجود | غير جاهز لتقرير كمية أو تكلفة فعلي حتى تكتمل الحركات والتكلفة. |
| المشتريات | دورة شكلية جزئياً | يحتاج استلام ومطابقة ثلاثية وقيود وضريبة مدخلة. |
| التقارير | تحليلية أكثر من محاسبية | لا تعتمد لإقفال أو قوائم مالية مدققة حالياً. |
| النسخ والاستعادة | غير مكتمل | خطر مرتفع لاستمرارية الأعمال. |
| الأمن والصلاحيات | جيد كبداية | يحتاج RBAC وظيفي، جلسات وإبطال ومراقبة أقوى. |
| زاتكا | أساس تكاملي فقط | **غير جاهز للربط أو الامتثال الفعلي** قبل التنفيذ الفني الرسمي. |

## 5. خارطة المعالجة المقترحة

### المرحلة الحرجة: منع الخطأ المالي قبل التوسع

ابدأ بمحرك ترحيل موحد لكل المستندات: بيع، شراء، صرف، قبض، مخزون، إنتاج، وتسوية. يجب أن يعمل داخل Transaction واحد، وأن يتأكد من الفترة المفتوحة، التوازن، الحسابات، رمز الضريبة، المخزون، والصلاحية قبل كتابة أي أثر. لا تُنفذ ميزة جديدة قبل إنهاء هذا المحرك واختباره.

بعد ذلك طبّق دورة POS قابلة للمراجعة: جلسة واحدة للكاشير، أسعار وتكاليف وضريبة من الخادم، تحصيل بحسب وسيلة الدفع، فرق صندوق، وإلغاء/استرداد مع اعتماد وقيد عكسي. ثم اكمل مخزوناً دائماً يرتبط بكل بيع وشراء وتحويل وإنتاج وجرد.

### المرحلة العالية: الإقفال والضريبة والمراجعة

ابنِ دفتر الأستاذ وميزان مراجعة حركي وقوائم مالية مستخرجة من القيود المرحلة. أضف منع الفترة المغلقة، إعادة فتح خاضعة للاعتماد، وتسويات شهرية. ثم أكمل ضريبة القيمة المضافة من الصنف إلى الفاتورة إلى القيد إلى تقرير المخرجات/المدخلات.

### المرحلة التنظيمية: زاتكا والاستمرارية

لا يبدأ اتصال زاتكا الفعلي قبل اكتمال صحة الفاتورة والضريبة. عندها ينفذ مولد XML والـ QR والتوقيع والتحقق المحلي وبيئة Sandbox ثم الإنتاج، وفق المواصفات ومتطلبات الأمن الرسمية [1] [2]. بالتوازي، نفذ نسخاً احتياطية فعلية واستعادة اختبارية وتقرير نجاح دوري.

## 6. قرار مهني صريح

**لا أنصح حالياً باستخدام النظام كمصدر وحيد للحسابات النظامية أو لإصدار فواتير زاتكا أو لإقفال شهري رسمي.** يمكن استخدامه في بيئة تجريبية أو تشغيل داخلي مراقب بعد تقييد الصلاحيات، لكن الانتقال إلى الإنتاج المالي يجب أن يسبقه إغلاق البنود الحرجة أعلاه واختبار سيناريوهات واقعية، مثل: بيع نقدي وبطاقة، مرتجع، خصم، تحويل مخزن، جرد بفروقات، إنتاج بهدر، فاتورة شراء وضريبة مدخلة، إقفال يومي، وإقفال شهري.

> **المعيار العملي للانتقال:** لا نعلن الجاهزية عند اكتمال الشاشات، بل عندما ينتج كل مستند أثراً محاسبياً ومخزنياً وضريبياً متسقاً وقابلاً للعكس والتدقيق، وتثبت ذلك اختبارات تكامل على بيانات واقعية.
