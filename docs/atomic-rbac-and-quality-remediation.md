# مصفوفة الصلاحيات الذرية وخطة إصلاح الجودة

## مبدأ التصميم

لا تمنح الصلاحيات بواسطة اسم دور ثابت في الشيفرة. يمنح المستخدم دوراً أو أكثر، ويمنح الدور صلاحيات ذرية مستقلة، ويمكن تقييد كل منحة بنطاق فرع أو مخزن أو مركز تكلفة. تكون صلاحية المدير هي الاستثناء المالك للنظام، لكن حتى المدير يمر عبر حارس الصلاحيات وسجل التدقيق.

> **قاعدة الفصل بين الواجبات:** لا يملك المستخدم الذي ينشئ مستنداً مالياً أو تشغيلياً حق اعتماده أو ترحيله إلا إذا منح له تفويض مستقل ومبرر. ويسجل الاستثناء في سجل التدقيق.

## بنية البيانات

| الكيان | الغرض |
|---|---|
| `roles` | تعريف الأدوار القابلة للإنشاء والتعطيل، مثل محاسب، كاشير، مدير فرع، أمين مخزن. |
| `permissions` | قاموس الصلاحيات الذرية الثابتة بالرمز والوصف والوحدة والإجراء. |
| `role_permissions` | منح صلاحية محددة إلى دور، مع خيار السماح أو المنع الصريح. |
| `user_roles` | ربط المستخدم بالدور ضمن نطاق اختياري. |
| `user_permission_overrides` | استثناء مباشر ومؤقت أو دائم لمستخدم محدد، مع السماح أو المنع. |
| `user_permission_scopes` | نطاق فرع أو مخزن أو مركز تكلفة عند الحاجة إلى تقييد المورد. |

## قواعد القرار

1. المنع الصريح للمستخدم له أولوية على أي سماح.
2. السماح المباشر للمستخدم له أولوية على سماح الدور.
3. الصلاحية لا تكون فعالة إلا إذا كان النطاق المطلوب ضمن النطاق الممنوح؛ والنطاق غير المحدد يعني كل النطاقات.
4. الدور المعطل أو المنحة المعطلة لا يدخلان في الحساب.
5. عمليات الإدارة المالية والحكومية تتطلب صلاحية محددة ولا تكتفي بمستخدم مسجل الدخول.
6. يجب تسجيل كل تعديل في دور أو صلاحية أو نطاق في `audit_log`.

## مصفوفة المسارات وحماية القراءة

لا تقتصر الحماية الذرية على عمليات الإنشاء والاعتماد؛ إذ تطبق كذلك على استعلامات القراءة التي تعرض سجلات مالية أو تشغيلية أو بيانات امتثال. تستخدم المسارات التي تقبل أكثر من وظيفة تشغيلية حارس `atomicAnyPermissionProcedure`، بينما تستخدم المسارات ذات التفويض الواحد `atomicPermissionProcedure`. وعند إدخال نطاق، يمرر حارس المسار الفرع أو المخزن أو مركز التكلفة إلى `hasAtomicPermission` قبل تنفيذ الاستعلام أو المعاملة.

| مجموعة المسارات | صلاحية القراءة أو التنفيذ المطلوبة | النطاق المطبق عند وجوده |
|---|---|---|
| لوحة التحكم والفروع | `accounting.reports.view` أو `admin.settings.view/manage` | دون نطاق |
| دليل الحسابات، مراكز التكلفة، القيود، الفترات، ميزان المراجعة والتخصيص | صلاحيات `accounting.*` المناسبة | فرع التقرير عند اختياره |
| الأصناف والمخازن وحركات المخزون | `inventory.catalog.manage` أو `inventory.view` | المخزن في `stock.byWarehouse` |
| التحويلات والجرد | `inventory.transfer.*` أو `inventory.count.*` | المخزن في إجراءات الإنشاء؛ والتحويلات تُراجع بصلاحية تشغيلية |
| الوصفات وأوامر الإنتاج وتقارير الإنتاج | `production.recipe.manage` أو `production.order.*` | المخزن والفرع في إنشاء أمر الإنتاج |
| الموردون وطلبات وأوامر وفواتير الشراء | صلاحيات `purchasing.*` المناسبة | المخزن أو الفرع عند إنشاء المستند |
| جلسات البيع والطاولات والطلبات والمطبخ | صلاحيات `pos.*` المناسبة | الفرع، ومركز التكلفة في طلب البيع |
| بيانات المنشأة والضرائب والعملاء والفواتير وطابور زاتكا | صلاحيات `compliance.*` المناسبة | دون نطاق في هذه النسخة |
| المستندات والإشعارات وسجل التدقيق والنسخ الاحتياطي | صلاحيات `admin.*` المناسبة | دون نطاق |
| تقارير المبيعات والربحية والمخزون والضريبة | `accounting.reports.view` أو صلاحية الوحدة ذات الصلة | فرع تقرير المبيعات عند اختياره |

### الاستثناءات المقصودة

تظل مسارات المصادقة العامة (`auth.me` وتهيئة الاعتمادات وتسجيل الدخول والخروج) عامة بحكم وظيفتها. أما `accessControl.myPermissions` فهو استعلام ذاتي للمستخدم المسجل، لا يعرض أدوار أو صلاحيات مستخدم آخر، ولذلك يتطلب جلسة موثقة فقط. لا توجد عملية مالية أو مخزنية أو تشغيلية أو إدارية حساسة تعتمد على `protectedProcedure` مباشرة؛ ويحمي الاختبار `server/route-permission-matrix.test.ts` هذا الشرط في كل تشغيل للاختبارات عبر تحليل شجرة TypeScript لـ`routers.ts` واستخراج كل إجراءات `query` و`mutation` ومراجعة الحارس ورموز الصلاحيات لكل مسار.

### إثبات نطاق مركز التكلفة

يغطي اختبار `server/atomic-rbac.test.ts` حالة سماح لإنشاء طلب POS في الفرع `4` ومركز التكلفة `55`، ثم يثبت رفض الطلب نفسه عند تغيير مركز التكلفة إلى `56`. كما يثبت تمرير نطاق مركز التكلفة من tRPC إلى إسناد الدور والتجاوز الفردي، وأولوية المنع الصريح ضمن النطاق نفسه. ويثبت اختبار `server/admin-cost-center-scope-ui.test.ts` ربط اختيار مركز التكلفة في واجهة المستخدمين بحملي tRPC للإسناد والتجاوز وعرضه بعد الحفظ. لا تجري هذه الاختبارات أي كتابة في قاعدة البيانات.

### اتساق الواجهة مع الخادم

يحمي اختبار `server/frontend-backend-rbac-alignment.test.ts` جميع عناصر التنقل المحمية من الانحراف عن حراس `PermissionOnly` لمساراتها. كما يتحقق تحديداً من تطابق صلاحيات المستندات والامتثال السعودي مع الحراس الذرية في الخادم. كشف الاختبار مسار وحدات قياس معلناً بلا Route، فتم ربطه بالشاشة المشتركة للتصنيفات ووحدات القياس؛ وبذلك لا تعرض القائمة الجانبية رابطاً محمياً بلا مسار أمامي.

يفحص `server/sensitive-action-rbac.test.ts` وجود `PermissionAction` ورمز الصلاحية المطلوب على أزرار الإجراءات الأعلى أثراً في الوحدات الرئيسية: دليل الحسابات، القيود اليومية، الفترات، مراكز التكلفة، التحويل والجرد، أوامر الإنتاج والشراء، التحصيل وجلسات نقاط البيع، إعدادات الامتثال، المستندات، والنسخ المشفر. يحافظ ذلك على قاعدة واضحة: صفحة قابلة للعرض لا تكفي لإظهار زر إنشاء أو اعتماد أو ترحيل أو إقفال ما لم تكن صلاحية الإجراء ذاتها فعالة.

## ترتيب إصلاح المخاطر

1. حارس تفويض ذري وتطبيقه على الترحيل والإقفال ونقاط البيع والتحويل والاعتمادات.
2. معاملة محاسبية ذرية موحدة مع منع عدم التوازن والفترة المغلقة.
3. محرك حركات مخزون موحد وسير اعتماد للشراء والإنتاج والجرد والتحويل.
4. تسوية النقد والإلغاء والاسترداد في نقاط البيع.
5. ضريبة القيمة المضافة، ثم زاتكا Sandbox، ثم الإنتاج.
6. نسخ احتياطي فعلي واستعادة اختبارية.
